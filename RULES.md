## 2. Политика коммитов

### 2.1. Правило завершённости (Только готовые функции)
* **Никаких незавершённых коммитов**: Запрещено коммитить недоделанный, сломанный или промежуточный код (не должно быть коммитов вроде "wip", "work in progress", "temp", "part 1", "checkpoint", "fix typo").
* **Атомарность**: Каждый коммит должен представлять собой логически завершённую, проверенную и рабочую функцию, оптимизацию или исправление.
* **Обязательная проверка перед коммитом**:
  - Код обязан успешно компилироваться: `cargo check --workspace`
  - Не должно быть регрессий в тестах: `cargo test` (или быстрый прогон `python tools/pr_ready.py --quick`).

### 2.2. Стандарт именования коммитов (Conventional Commits)
Названия коммитов должны быть ясными, понятными человеку и структурированными по стандарту:

```text
<тип>(<область>): <краткое и понятное описание сути изменений>

[Необязательное подробное описание: что именно сделано, почему и как протестировано]
```

#### Допустимые типы коммитов:
* `feat`: Добавлена новая завершённая функция или возможность (попадает в ченджлог в раздел «Новые функции»).
* `fix`: Исправлена ошибка, вылет или некорректное поведение (попадает в раздел «Исправления»).
* `perf`: Оптимизация производительности или использования памяти (попадает в раздел «Производительность»).
* `refactor`: Изменение структуры кода без изменения функциональности или интерфейса.
* `docs`: Обновление документации, правил, руководств или ченджлога.
* `test`: Добавление, расширение или исправление тестов.
* `chore`: Обслуживание репозитория, обновление версий зависимостей, скрипты сборки.

#### Примеры понятных названий коммитов:
* `feat(renderer): реализована поддержка динамического освещения от факела в руке`
* `fix(worldgen): устранено аварийное завершение при генерации биома Deep Dark`
* `perf(chunk-mesher): оптимизировано построение сетки вокселей с помощью SIMD`
* `docs(readme): обновлено руководство по быстрой установке форка`
* `chore(release): подготовка релиза v0.2.0`

### 2.3. Автоматический контроль (Git Hook commit-msg)
В репозитории настроен хук `.githooks/commit-msg`, который отклоняет коммиты с невнятными названиями (например, короче 10 символов, без указания типа или с фразами "wip", "fix").

## 4. Система ченджлогов для GitHub

### 4.1. Формат CHANGELOG.md
Файл `CHANGELOG.md` ведётся по стандарту [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/) и содержит:
1. Секцию **`[Unreleased]` (В разработке)** в верхней части файла. Все новые завершённые функции и исправления накапливаются здесь до момента релиза.
2. Именные секции версий: `## [vX.Y.Z] — ГГГГ-ММ-ДД`.
3. Подразделы по категориям:
   - `### ✨ Новые функции` — всё новое для игроков и разработчиков.
   - `### 🐛 Исправления ошибок` — устранённые баги и сбои.
   - `### ⚡ Производительность` — ускорения и оптимизации.
   - `### 🔄 Изменения` — изменения в существующем поведении.
   - `### 🛡️ Безопасность и Лицензии` — безопасность и лицензионные обновления.

### 4.2. Автоматический помощник `tools/terrarich_changelog.py`
Для генерации и ведения ченджлога разработан скрипт:
```bash
# Просмотреть накопившиеся изменения с последнего тега:
python tools/terrarich_changelog.py

# Сформировать описание релиза для GitHub в файл RELEASE_NOTES.md:
python tools/terrarich_changelog.py --notes

# Перенести блок [Unreleased] в новую версию (например, v0.1.0) в CHANGELOG.md:
python tools/terrarich_changelog.py --bump v0.1.0
```

## 5. Система публикации релизов (Строго по команде Terrarich)

### 5.1. Принцип: Никаких спонтанных автоматических релизов
* Автоматическая публикация релизов по таймеру (cron каждые 10 минут) и по завершению CI отключена.
* **Релиз публикуется ИСКЛЮЧИТЕЛЬНО тогда, когда Terrarich даёт явную команду на публикацию**.

### 5.2. Удобный инструмент релиза: `tools/terrarich_release.py`
Скрипт релиза автоматизирует весь цикл выпуска новой версии в безопасном пошаговом режиме.

#### Быстрый запуск релиза:
```bash
# Интерактивный запуск (скрипт сам спросит версию и покажет все шаги):
python tools/terrarich_release.py

# Запуск с указанием версии:
python tools/terrarich_release.py --version v0.1.0

# Безопасный предварительный просмотр (Dry-run без создания тегов и коммитов):
python tools/terrarich_release.py --version v0.1.0 --dry-run
```

#### Что выполняет скрипт релиза:
1. **Проверка чистоты репозитория**: убеждается, что нет незакоммиченных изменений и ветка актуальна.
2. **Проверка компиляции**: проверяет проект через `cargo check`.
3. **Генерация ченджлога**: собирает все коммиты, переносит `[Unreleased]` в новую версию в `CHANGELOG.md`.
4. **Создание релизного коммита**: фиксирует изменения ченджлога (`chore(release): vX.Y.Z`).
5. **Создание Git-тега**: создаёт аннотированный тег `vX.Y.Z` с автором Terrarich.
6. **Генерация описания для GitHub Releases**: сохраняет готовый файл `RELEASE_NOTES_vX.Y.Z.md`.
7. **Инструкция отправки**: выдаёт точную команду для отправки на GitHub (`git push origin main --tags`).

### 5.3. Ручной запуск через GitHub Actions (`workflow_dispatch`)
В репозитории создан рабочий процесс `.github/workflows/terrarich-release.yml`:
* Запускается **вручную** через вкладку **Actions -> "Terrarich Manual Release" -> "Run workflow"**.
* В диалоговом окне указывается:
  - Тег версии (например, `v0.1.0`);
  - Заголовок релиза;
  - Отметка Draft или Pre-release (по желанию).
* Сборка и публикация релиза происходят на серверах GitHub Actions строго по нажатию кнопки.
